# Business data export

Open **Backup export** at `/app/backup-export`. Select **Create Export** once; the page updates automatically and shows **Download Export** when ready. The page shows only a short status and the action needed. Existing list/form Create Export actions lead to this page, and unsaved tracking forms redirect there. The standard Backup export list/form remains available for administrative history. No database restore, email delivery, or business attachments are included.

## Request limits

The entire site may request one export per rolling 24 hours and at most two per rolling seven days. All users and company scopes share this quota. Accepted requests count in every status, including failed jobs and queue failures; rejected requests do not create a record or consume another slot. Downloading an existing valid export does not consume quota. The exact 24-hour and seven-day boundaries are eligible again. A site-wide request lock protects the quota check and committed tracking record against concurrent requests; the database read is refreshed after obtaining the lock.

## Authorization and ownership

Each Frappe site database is one client tenant. The server uses the current authenticated site connection; the request API accepts no site or company parameter. Sanawbar owns this cross-site feature as explicitly requested. It does not import a consumer application or make ERPNext an installation dependency. Generation requires the ERPNext business tables and a MariaDB/InnoDB source database; a Frappe-only installation fails closed.

Assign **Business Data Exporter** to an enabled client administrator account. This role is the sole application permission for exporting business data: it grants access to all companies in the current site's database, independent of Company User Permissions and source DocType/document read permissions. System Manager and the Administrator account do not substitute for explicit assignment of the export role. Any enabled role holder in the same site may download a valid export, including one requested by another role holder. Requester identity is retained for audit, not used as an additional access restriction.

The server rechecks enabled account and explicit role assignment at request, execution, immediately before publication, status polling, and download. Expiry, file-integrity checks, and the current-site boundary still apply. The worker rechecks the original requester's role; revocation before publication fails the job. The history DocType grants read access to this role without an owner-only restriction; direct tracking-record writes remain blocked by the controller.

Company-bearing transactions and masters are selected by company, child rows by their explicitly allowed parent type, field and ID. Other masters are reached through enumerated business relationships. Employee masters are selected by company, including records without a transaction reference. If the scope contains every company in the site, all site-owned customers, branches, items, suppliers, and other site-level business masters are included, even those without transactions. With a narrower scope, only referenced site-level masters are included because the standard masters have no company ownership field. Company-specific Customer/Supplier account children are filtered again. A relationship to an existing record in an unauthorized company fails the export; it never expands the authorized scope.

## Data contract

The [exact source field allowlist](business-export-schema.md) and `sanawbar/business_export/schema.json` define the version 6 schema. Newly installed DocTypes, custom fields, or upstream fields are never included automatically. Supporting tables cover those financial records and the additional business history described below.

Configured accounting dimensions are inspected only to validate compatibility, not exported as application configuration. Branch, Project and Cost Center are supported. Other configured dimensions, including disabled historical dimensions, fail closed until explicitly supported. A ledger or allocation that references an unsupported voucher/party type also fails closed. This prevents silent omission of financial context. Deleted/missing targets are not synthesized; existing reference IDs are preserved. Optional tables absent in an older installation produce empty destination tables; absent allowed columns produce NULL.

The ZIP contains only `business-data.sql`: executable SQLite 3 SQL with independent neutral table names and short, independently named columns. No manifest, data dictionary, README, or instruction file is included. The schema documentation remains in this repository and should be provided separately to clients who need to interpret or migrate the data.

Snapshot time, company scope, table counts and the complete ZIP's SHA-256 checksum remain in the private tracking record. The checksum is verified again before download.

All SQLite columns use TEXT affinity. Exact decimal strings avoid SQLite floating-point rounding, including very large values, trailing zeroes and fractional precision. Consumers should use decimal arithmetic, not SQLite REAL or floating-point `SUM`, for financial calculations. Integers and booleans are represented as decimal strings; 0 and false are preserved. Absent values are SQL NULL. Strings use UTF-8 hexadecimal text literals, safely preserving quotes, backslashes, newlines, NUL and Arabic text. Source DECIMAL decoding is explicitly overridden because Frappe otherwise converts it to float.

Each SQL table and column uses a stable, concise alias rather than the source DocType or long field name. For example, `Sales Invoice` becomes `sales_bills`, `Stock Ledger Entry` becomes `stock_gl_rows`, and `Customer` becomes `clients`. For example, `grand_total` becomes `grand_amt` and `total_taxes_and_charges` becomes `total_tax_chgs`. Every table uses `id` for the original document ID and `state` for document status (0 draft, 1 submitted, 2 cancelled). Child tables use `parent_id`, `parent_tbl`, `bucket`, and `seq` for parent ID, neutral parent table, neutral collection and position. The collection is usually the child table name; where one child table serves several collections under the same parent, it uses a distinct neutral label. The external [column dictionary](business-export-schema.md) gives the exact alias-to-source mapping. All document statuses are included. Ledger `is_cancelled` and payment ledger `delinked` flags are preserved; consumers must apply these flags when computing current balances. Do not add POS and consolidated sales invoices together without following `consolidated_invoice`, `pos_invoice` and their line links.

Original document IDs remain unchanged. If MariaDB resolves a reference with different case or spacing to an existing document, the exported reference uses that document’s exact ID so SQLite joins work. The original reference spelling is preserved in the fixed `raw_refs` JSON column, keyed by exported column alias; otherwise that column is NULL. Missing targets are never synthesized. Static links target the mapped table's `id`; dynamic document-type values are replaced by independent destination table names. `voucher_detail_no` and `reference_detail_no` retain source line IDs. Tax `row_id` references a tax row position within the same parent, not a globally unique ID. `item_wise_tax_detail` and `item_tax_rate` remain their original JSON text. Existing unbalanced or inconsistent accounting is preserved, not recalculated or “repaired.”

Users, roles, sessions, passwords, credentials, integration settings, scripts, workflows, application metadata, customizations, internal logs and the tracking records themselves are excluded. Source user ownership/audit identities are not exported. Descriptive business text remains client-entered text. This is client-owned portable data that can be mapped into another system; it is not a directly restorable Frappe application.


## Coverage and limits

Version 6 uses 115 explicitly allowlisted independent tables. It covers company, customer, supplier, employee, product, price, unit, address, contact, bank-account and bank-transaction records; invoices, quotations, orders, material requests, receipts, payments, allocations, journal and ledger records; stock movements and valuation entries; POS opening, closing and invoice-consolidation history; item tax definitions, landed costs, batch/serial records, assets, expenses, EV charging sessions, and URY restaurant/menu, order, kitchen, partial-closing and daily profit records. Empty allowed tables are emitted as empty SQLite tables so the schema remains stable across sites. [The complete table and field list](business-export-schema.md) is the authoritative coverage contract.

The ZIP contains only SQL. Binary attachments, product images, invoice PDFs and other File records are excluded. Printer routing, user accounts, role assignments, credentials, integration settings, application customizations and logs are excluded. Some source business documents may have site-specific custom fields; these are excluded until each field receives an explicit business-data review. Derived summary tables such as Bin are omitted because stock ledger history is included; daily profit summaries are included as reported summaries and must not be added to ledger amounts as separate transactions.

Business relationships retain their target identities, original reference spellings remain recoverable through `raw_refs`, and enumerated document-type discriminator values become neutral export table names. Identifiers and client-entered text can still contain names chosen in the source system; the export does not alter that business data. The SQL does not contain Frappe's DocType metadata or application code, and cannot restore the application. It remains portable client data that can be imported or transformed by another system.

## Snapshot, jobs and private storage

The worker opens a separate connection to the current site's database and starts `REPEATABLE READ` with `WITH CONSISTENT SNAPSHOT, READ ONLY`. All business reads share that transaction. Included source tables must use InnoDB. Metadata inspection only checks the availability of the already allowlisted columns and storage engines; it does not discover additional export fields. Live export-role authorization is checked independently from the business snapshot.

A site-namespaced Redis scope lock and a persisted Queued/Running record prevent concurrent exports for the same exact company set, including requests from different administrators. Jobs use the long queue with a 55-minute timeout; locks expire after one hour. Publication happens by atomic rename only after the complete ZIP and authorization checks succeed. Failures remove the artifact, retain a generic failure message in history, and send details only to the server error log. Queue failures and abandoned jobs are recoverable.

ZIPs live in `sites/<current-site>/private/business_exports`, outside `/private/files`. There is deliberately no ordinary Frappe File attachment: its owner/share shortcuts could bypass revocation and expiry. The tracking record holds the private filename; the authenticated endpoint is the only supported download path. Responses are attachments with `Cache-Control: no-store, private`. Staging directories are private and published ZIPs have mode 0600.

Download access ends exactly 24 hours after publication. The scheduler deletes expired ZIPs every five minutes and keeps the history record. Physical deletion may lag by up to the scheduler interval, and longer if the scheduler is stopped; expiry authorization does not depend on the scheduler. Abandoned jobs older than two hours become Failed once their lock is available. Orphan staging files are removed afterward.

Generation currently materializes the selected records in worker memory; downloads materialize the ZIP. Large sites need adequate worker memory, queue capacity and time. No incomplete export is provided if those limits are exceeded. Administrative filesystem access and database superuser access remain outside this application authorization boundary.

## Installation and checks

On a future authorized deployment, normal app migration registers the DocType and scheduler hook; the after-install/after-migrate hook creates the role without assigning it to anyone. Assign the role to intended client administrators. Normal migration also registers the Backup export Desk page and updates the history read permission. A long-queue worker and scheduler must run. No sites were migrated as part of this implementation.

The page uses native Frappe Desk controls, with translated text, keyboard-accessible actions, a live status region and 44px action targets.

Focused tests: `../../env/bin/python -m unittest sanawbar.tests.test_business_export` from the app directory (use the bench's actual environment path). Run Ruff on the changed Python files and `node --check` on the two Desk scripts. The tests import generated SQL into SQLite and cover exact decimals, relationships, ledger/payment reconciliation, isolation, unauthorized access, failures and expiry. A live read-only MariaDB snapshot check can validate the installed source dialect without changing business data. End-to-end DocType migration, Redis worker and browser checks belong on an isolated test site before production rollout.

## Live verification, 15 October 2026

A read-only audit of `ury-test.sanawbar.net` generated the SQL-only ZIP from the production snapshot reader, imported it into a fresh SQLite database, and compared it to independent reads within the same MariaDB snapshot. The final snapshot was taken at 21:07:24 Asia/Amman (18:07:24 UTC). Verification covered 115 tables, 160,219 actual source records, 4,229,227 source field values, 808,256 existing reference targets and 11 exact accounting/quantity aggregate comparisons. SQLite integrity checks passed. There were no unresolved references. The temporary ZIP was 6,963,733 bytes and was deleted with the temporary SQL and SQLite files.

The review corrected landed-cost line references that can target either purchase invoices or purchase receipts, the source field for stock additional-cost totals, inclusion of stock additional-cost child rows, and the actual asset opening-depreciation/scrap-journal fields. It also found 505 existing child references with spacing differences that MariaDB accepts; these now join correctly in SQLite while preserving their original spelling in `raw_refs`.

Count differences were explained: unused currencies (148), units (230), and one unused fiscal year are supporting masters outside the referenced selection; one sales-tax template row, nine purchase-tax template rows, and one customer-group account-default row are excluded configuration. All company-scoped transaction roots and all site-master roots matched the source counts on this site. This verifies the current allowlist, not completeness for unreviewed custom business fields or DocTypes.

Repeat the audit from the bench with `bench --site SITE execute sanawbar.tests.verify_business_export.verify_current_site`. It uses the current site connection, creates private temporary artifacts, and returns counts and discrepancies. It does not publish a download, create tracking records, consume request quota, or modify business data. Queue-worker, role, download and expiry behavior is covered by focused tests; this audit did not migrate the site or exercise the browser/background queue end to end.
